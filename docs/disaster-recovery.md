# Disaster recovery

How to recover a Bastion node after data loss, and how to move it to a new host.
Read this **before** you need it.

## 1. What is irreplaceable vs. disposable

| Path | Contains | If lost |
|---|---|---|
| `stack-bitcoin/data/cln/hsm_secret` | The CLN wallet seed. | **Total loss.** On-chain funds cannot be swept, channels cannot be closed. No backup = no recovery. |
| `stack-bitcoin/data/cln/lightningd.sqlite3` | Channel state, payments, the node DB. | Force-close of every channel at best; **funds stolen** if a stale copy is restored while a peer has newer state (penalty). |
| `/backup_usb/lightningd.sqlite3` | Live replica written by the CLN `backup` plugin + `services/bastion-daemon.sh`. | Your primary DB restore source. Keep the USB healthy. |
| `stack-bitcoin/data/cln/emergency.recover` | CLN Static Channel Backup (SCB). | Lets peers help you force-close after a full DB loss. `bastion-daemon.sh` snapshots it to `/backup_usb/history/` daily. |
| `stack-bitcoin/data/teos/` | The watchtower tower key (only if you run `teosd`). | The tower gets a new identity; clients must re-register. Not fund loss. |
| `bastion.conf` + `secrets/` | Generated config + secrets (git-ignored). | Regenerated by `./bastion`, but you re-enter WireGuard URL/port, node alias, and any tokens. Back it up. |
| `bastion-tor-data` volume | Tor's `DataDirectory`. | **Disposable.** Recreated on next start. |
| `stack-bitcoin/data/cln/.../gossip_store` | The gossip graph. | **Disposable.** Rebuilds from the network. |

**The `.onion` is stable.** CLN uses `statictor:` (`stack-bitcoin/config/cln_config`),
so the hidden-service key is derived from `hsm_secret`, *not* from Tor's data
directory or `bind-addr`. A rebuild or host move keeps the **same** `.onion` — no
re-announce, no lost inbound.

## 2. Back up (do this now, and on a schedule)

With the node **stopped cleanly** (`docker exec lightningd lightning-cli stop`,
then `./bastion stop stack-bitcoin`):

```bash
tar -czf bastion-backup-$(date +%F).tgz \
    stack-bitcoin/data/cln \
    stack-bitcoin/data/teos \
    bastion.conf secrets/
```

Store it off the host (encrypted). `bastion-daemon.sh` already keeps the SCB and a
daily `lightningd.sqlite3` replica on `/backup_usb`; this tarball is the
point-in-time complement.

## 3. Restore on the same host

1. `./bastion down` and confirm no `lightningd` / `bitcoind` containers remain.
2. Restore the tree:
   ```bash
   tar -xzf bastion-backup-<date>.tgz
   ```
   Use the **newest** `lightningd.sqlite3` you have — the `/backup_usb` replica is
   usually newer than a nightly tarball. **Never** restore an older DB than the
   one the node last ran with: a peer with newer channel state can broadcast a
   penalty and take the channel balance.
3. `chown` the restored `data/` back to the host user if needed.
4. `./bastion up`.
5. Run the [verification checklist](#5-verification-checklist).

## 4. Move to a new host

1. New host: install Docker + Compose, `git clone` this repo at the same commit,
   `git submodule update --init --recursive`.
2. Copy `stack-bitcoin/data/cln`, `stack-bitcoin/data/teos`, `bastion.conf`,
   `secrets/` from the old host (see §2 for a clean copy).
3. `./bastion up`. Networks and the `bastion-tor-data` volume are recreated
   empty — expected.
4. The node comes back on the **same `.onion`**. `trustedcoin` re-syncs block
   headers over Tor (a few minutes). Peers reconnect on their own or when you
   `lightning-cli connect` them.
5. Decommission the old host only after a few days of confirmed stable operation
   on the new one — keep the old `data/` copy until then.

## 5. Verification checklist

```bash
docker exec lightningd lightning-cli getinfo
```
- `id` unchanged, `address` shows the **same `.onion`** as before.
- `blockheight` is advancing (trustedcoin has synced).

```bash
docker exec lightningd lightning-cli listpeerchannels     # channels present, expected states
docker exec lightningd lightning-cli listfunds            # on-chain + channel balances match
docker exec lightningd lightning-cli listpeers            # peers reconnecting / connected
```
- RTL loads at `http://<host>:3000` (the rune in `stack-bitcoin/data/rtl/access.rune`
  is tied to this node; it survives a restore).
- If you run `teosd`: `docker logs teosd` shows the tower registered its onion;
  `lightning-cli listconfigs | grep -i watchtower` shows the client is configured.

## 6. Never

- **Never** roll `lightningd.sqlite3` back to an older copy than the node last
  used (penalty / theft risk).
- **Never** `docker volume prune` / `docker system prune --volumes` on this host —
  it would take `bastion-tor-data` (harmless) but the habit is dangerous; CLN
  state lives in bind mounts under `data/`, so a mistaken prune of a *named*
  volume you added later could still hurt.
- **Never** run two copies of the same `hsm_secret` / DB against the network at
  once (old host + new host both up) — that is the classic way to get penalised.
